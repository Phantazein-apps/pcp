# PCP v0.3 plan: scope, outline, decisions

Status: Phase 1 output (informative). Written 2026-10-18.
Evidence for every claim here is in [`v0.3-audit.md`](v0.3-audit.md).

## 1. Goal

v0.3 is the first PCP version two independent implementations can build
against and test each other with:

- **MultiPass**: one person's hosted context, with user-held keys.
- **Agent Brain**: a team's agent memory on a WordPress server the team or
  its host controls.

v0.3 is done when:

1. Both can describe themselves truthfully in `/.well-known/pcp.json`.
2. A client written once can call either of them.
3. Each can import the other's export.
4. A runnable suite says which of these holds.

## 3. Core vs extension

The rule: anything an export must carry for a round trip to be lossless is
core. Anything a context can lack without changing what its memory means is
an extension.

| Feature | Placement | Why |
|---|---|---|
| Discovery, auth, profile.core (personal kind), memory, scopes, audit, export, import | Core | Unchanged |
| Context `kind` and controller | Core | Export and consent depend on it |
| Principals | Core | Every write needs an author for provenance; a personal context is a team of one |
| Partitions with a per-principal ACL | Core, optional to use | A personal context has one partition. Agent Brain's partitions must survive export. |
| Review state on pages | Core field, optional workflow | Imports entering review needs the field everywhere |
| Erasure with receipt | Core | A user right, and Agent Brain already has it |
| Shared documents (artifacts, sections, leases, versions) | Extension | Large; no other implementation; does not change memory semantics |
| Handoffs between principals | Extension | Same |
| Sensitive profile namespaces (`pcp.health` etc.) | Extension, as today | Unchanged |
| Connections | Extension, as today | Unchanged |
| Management API | Informative | Unchanged |

Extensions for documents and handoffs would be drafted by Agent Brain's
maintainers under their own prefix, with PCP reserving the slot. That keeps
Agent Brain's design in Agent Brain's hands, and keeps product names out of
the generic spec.

### 3.1 Landscape inputs each phase should use

Detail and sources are in audit §10.

- **Phase 2 (model):**
  - Reuse OKF's provenance names: `generated: {by, at}` and `verified: [{by, at}]`.
  - Use OKF actor syntax for principals.
  - Add transaction time (`recorded_at`) next to valid time, plus an `as_of` search parameter (Graphiti, Remnic).
  - Add `source.basis: provided | observed | inferred` (GDPR Art 20).
  - The server stamps who wrote a page; the caller never supplies it (Remnic `sharedBy`).
  - Agents read with the intersection of their own grant and the delegating person's access (supermemory Company Brain).
  - Allow namespaced extension relations, so imports stay lossless.
  - Take review verbs from MemoryLake and Remnic.
- **Phase 3 (export):**
  - Write importer mappings in `interop.md` for Agent Brain, Basic Memory, Mem0, supermemory, OMP, Remnic and DTI conversations.
  - Add an optional OKF projection.
  - Publish a JSON-LD `@context`.
  - Register the schemas on Schemas.pub.
- **Phase 4 (keys):**
  - User-sole key custody by default.
  - Any recovery share is opt-in and declared (unlike MemoryLake's 2-of-3).
  - Indexes count as content (unlike Remnic's at-rest encryption, which leaves the index out).
- **Phase 5 (conformance):** track the W3C AI Agent Memory Interop CG's conformance tests for export and erasure.

## 4. Deferred to v0.4

- Federation and shared scoped context between contexts (family plans).
- Push vs pull ingestion contract for connections; connection tool schemas.
- Schemas for `pcp.residency`, `pcp.legal`, `pcp.family`, `pcp.finance`,
  `pcp.home` (if D10 is accepted).
- Normative memory merge and supersession rules beyond `relations`.
- Searchable encryption; the Confidential (enclave) tier's attestation claim.
- DPoP and sender-constrained tokens (MCP roadmap item, still a draft).
- A Solid pod bridge and formal mapping to the W3C memory community group's
  profiles.
- Standardizing the management API.

## 5. Phase plan

The five phases stay. Two adjustments:

1. **Phase 2 also defines "what a context is".** That covers context `kind`,
   controller, and the `encryption` vocabulary as discovery fields. Phase 3's
   manifest needs these, and they are part of the model. Phase 4 then
   specifies the semantics: key custody, identity binding, offboarding.
2. **Phase 2 also lands the cross-cutting §5 to §7 fixes** (tool names, path
   grammar, `updated`, sensitivity, merge patch, audit fields). They touch
   the same text as the team model, and splitting them would mean editing
   the same sections twice.

| Phase | Name | Deliverables | Depends on |
|---|---|---|---|
| 2 | Team context model | SPEC §1, §4 to §7 edits; frontmatter, discovery and audit-entry JSON Schemas; Agent Brain mapping table (normative appendix or `docs/`); tool rename; extension slot for documents and handoffs | D1, D2, D3, D13, D14 |
| 3 | Export and import | §8 rewrite; manifest schema and a real example archive under `examples/`; import rules; erasure receipt; `interop.md` importer mappings; cherry-pick and rework `3a8b8a8` | Phase 2 schemas, D8, D11 |
| 4 | Auth, keys and contexts | §2 auth fields, §3 rewrite, §9; work vs personal semantics; user-held key profile; encryption definitions | D4, D5, D6 |
| 5 | Conformance and release | v0.3 `conformance.md`; runnable suite; runs against MultiPass and the Agent Brain demo; release PR; briefs for Roger and the multipass.host session | All |

Each phase PR merges to `main` under an "in progress" banner (D7).

## 6. Decisions needed from Dennis

Each decision has a recommendation. **Bold** marks the ones that touch the
MultiPass privacy promise or principle 8. The rules say to ask before
changing either, so those are flagged.

| # | Decision | Options | Recommendation | Needed by |
|---|---|---|---|---|
| D1 | Tool name convention | (a) keep dots; (b) `<part>_<verb>` snake_case; (c) define dot/underscore/hyphen equivalence | **(b)**: `profile_get`, `memory_search`, `context_brief`, at most 40 chars. It is the only form every client and model API passes unchanged. Servers MAY accept the v0.2 dotted names in `tools/call` for one version but MUST NOT list them. Connection ids become `[a-z][a-z0-9]{0,15}` so `notion_search` splits cleanly. | Phase 2 |
| D2 | Team model placement | (a) all of it in core; (b) principals, partitions and review in core, documents and handoffs as extensions; (c) everything team-related as one extension | **(b)**. Export must carry principals, partitions and review state, so they cannot be optional to understand. Documents and handoffs are Agent Brain's design to own. | Phase 2 |
| **D3** | Work vs personal | (a) personal only; (b) personas inside one context; (c) separate contexts, each with a `kind` and a controller | **(c)**. Principle 5 says separate contexts, keys and identities. It is the smallest spec change: §2.1 already supports many contexts per host. A client can be bound to one context by its token audience (RFC 8707). Touches the promise, so flagged. | Phase 2 (field), Phase 4 (semantics) |
| **D4** | Encryption vocabulary | (a) keep `{at_rest, e2e}`; (b) replace with `key_custody: host \| user \| device` plus `readable_by`, with `e2e` reserved for `device` | **(b)**, with definitions: `user` means the host decrypts only during a request the owner authorized; `device` means plaintext never exists off the owner's devices; indexes and embeddings are content. This lets MultiPass Hosted describe itself truthfully without the word "end-to-end", as principle 6 requires. Touches the promise, so flagged. | Phase 2 (field), Phase 4 (semantics) |
| D5 | MCP baseline | (a) 2026-07-28 only; (b) MUST interoperate with 2025-11-25 and 2026-07-28, MAY support older; (c) leave unspecified | **(b)**. PCP semantics should not depend on sessions, so they hold under both revisions. | Phase 4 |
| D6 | Client registration | (a) DCR REQUIRED (today); (b) CIMD SHOULD, DCR MAY | **(b)**, matching MCP 2026-07-28, where DCR is deprecated. Agent Brain then passes; MultiPass should add CIMD (a MultiPass task, not spec work). | Phase 4 |
| D7 | Branch and release strategy | (a) each phase PR merges to `main`; (b) one long-lived `v0.3` branch merged at Phase 5 | **(a)**, after tagging `v0.2-draft` on `ea1a1fa` now, so implementers can pin. `SPEC.md` carries an "in progress" banner until Phase 5. | D10 | Reserved namespaces | (a) write all five schemas in v0.3; (b) v0.3 rule: no data in a reserved namespace until its schema is published, schemas in v0.4 | **(b)**. It prevents incompatible shapes now at almost no cost, and no implementation stores these categories yet. | Phase 2 |
