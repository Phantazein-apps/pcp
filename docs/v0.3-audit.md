# PCP v0.3 audit: spec vs implementations, and alignment

Status: Phase 1 working document (informative). Written 2026-10-18.
Companion: [`v0.3-plan.md`](v0.3-plan.md) (scope, outline, decisions).

This audit compares PCP v0.2-draft (`SPEC.md`, `schemas/`, `docs/`, last
changed 2026-07-07) with the three codebases that implement or nearly
implement it, then checks it against current MCP rules and the memory
landscape. Nothing in this document is normative.

## 1. Summary

- **No implementation conforms, and no two implementations agree on a tool name.**
  MultiPass serves `memory.search`, Agent Brain serves `agent-brain-memory-search`,
  pcp-wp served `pcp-memory-search`. Claude Code shows MultiPass's tools as
  `memory_search` because the client rewrites dots, not because MultiPass
  diverges. The Notion "known gap 3" is therefore a client-compatibility
  problem in the spec, not drift in MultiPass.
- **Export, the first design principle, is built nowhere.** MultiPass
  advertises `export: false`. Agent Brain exports per-row Markdown without
  `title`, `updated`, a manifest or checksums, and has no import. Both
  products' landing pages promise PCP export.
- **Both live products are ahead of the spec on OAuth discovery.** Both serve
  RFC 9728 protected resource metadata (root and path-suffixed) and a
  `WWW-Authenticate` challenge, which §3 does not mention. Agent Brain uses
  CIMD and has no DCR, so it fails a §3 MUST that current MCP no longer
  requires.
- **The spec cannot describe Agent Brain.** It has no principals inside a
  context, no memory partitions, no review state, no shared documents, no
  erasure operation and no team profile. Agent Brain's OAuth scope is the
  single string `mcp`; its real authority is a server-side ACL per partition.
- **The spec cannot describe MultiPass's launch promise either.**
  `encryption: {at_rest, e2e}` has no way to say "user-held keys, decrypted
  only during an authorized request". §5.2 assumes a persistent server-side
  plaintext index, which MultiPass's key design forbids. Work and personal
  contexts have no field.
- **There are real security divergences to fix in the products** (listed in
  §4.3 and §5.3). The most serious: a MultiPass `memory:write` token can
  silently downgrade a sensitive page to normal, and revoking a MultiPass
  grant after a refresh returns success while the live token survives.
- **The spec contradicts itself in about a dozen places** (§3 below): version
  labels, root discovery, `_index`, `updated`, path grammar, SSE, and the
  dangling §8 link (fixed in this phase).

## 3. Defects inside the spec itself

These are problems an implementer meets by reading `SPEC.md` alone.

| # | Where | Defect | Assigned to |
|---|---|---|---|
| S1 | §2 example, §10, `profile.core.schema.json` | The document is v0.2-draft, but discovery says `"pcp_version": "0.1"`, the profile schema pins `const "0.1"`, and §10 offers "PCP v0.1 conformant". No rule says what a v0.2 server emits. | Phase 5 (versioning rule now, in plan) |
| S2 | §2 vs §2.1 | `mcp_endpoint` is REQUIRED, but §2.1 says the origin-root document of a multi-context host has "no tenant specifics", so it cannot have one. MultiPass resolved this by adding `context_url_template`. | Phase 4 |
| S3 | §8 | Linked `[schemas/export.manifest.schema.json]`, a file that does not exist on `main`. **Fixed in this phase** by pointing at the v0.3 plan. | Done; schema in Phase 3 |
| S4 | §3 | DCR is REQUIRED; RFC 9728, `WWW-Authenticate`, CIMD and RFC 8707 are absent. Both live products already do more than §3 says, and Agent Brain fails the DCR MUST while working with claude.ai. | Phase 4 |
| S5 | §3 | "Tokens per client-device pair" has no OAuth meaning; no implementation captures a device. | Phase 4 |
| S6 | §3 | "SSE (OPTIONAL)" does not say whether it means the deprecated HTTP+SSE transport or the stream inside Streamable HTTP. | Phase 4 |
| S7 | §6 | Dotted tool names are not portable across clients (see §9.1). | Decision D1, Phase 2 |
| S8 | §5 | No path grammar. pcp-wp lowercased and turned `.` into `-`, which breaks `style/{context-id}.{lang}` from `docs/style-profiles.md`. MultiPass allows `..` and a leading `/`, which an archive importer must reject. | Phase 2 |
| S9 | §5, §6 | `_index` is ambiguous: a page, or a manifest? PACK uses `index.md`. Neither implementation maintains one, so `memory.list` "read `_index`" means nothing. | Phase 2 |
| S10 | §5.1 | `updated` is REQUIRED but its format is not given, nor whether the server stamps it or keeps an imported value. Both MultiPass and pcp-wp emit `YYYY-MM-DD HH:MM:SS`. | Phase 2 |
| S11 | §5.1 | "Stale by definition" when `valid_until` has passed: computed at query time or stored? | Phase 2 |
| S12 | §5.1 | `sensitivity` is a frontmatter key, but the tool surface never says whether `memory.write` takes it from frontmatter or a parameter. MultiPass takes a parameter and ignores YAML, so a spec-following client that writes `sensitivity: sensitive` in the body gets a normal page. | Phase 2 |
| S13 | §5.2 | `style/` SHOULD default to sensitive, but it does not say who applies the default. Neither implementation does. | Phase 2 |
| S14 | §7.1 | No `memory.sensitive:write`, so a write token can overwrite or downgrade a page it cannot read. | Phase 2 |
| S15 | §6, §7 | No defined behavior for insufficient scope (HTTP 403 `insufficient_scope`, a tool error, or hiding the tool). | Phase 4 |
| S16 | §6 | `profile.update` "patch semantics" is not defined. MultiPass does a shallow merge with `null` deletes; RFC 7396 is the obvious choice. | Phase 2 |
| S17 | §7.3 | The audit log is REQUIRED but has no schema, and nothing says whether it may contain content. MultiPass logs raw search queries and page paths, against its own security model. | Phase 3 (export) and Phase 2 (fields) |
| S18 | §2 | `encryption.at_rest` and `encryption.e2e` are undefined. MultiPass reports `at_rest: true` for plaintext rows on an encrypted platform disk. | Phase 4 |
| S19 | `docs/interop.md` | Unknown import keys go under `x_import`; pcp-wp kept the raw frontmatter instead. Pick one. | Phase 3 |
| S20 | Schema `$id`s | All schema `$id`s use `https://pcp.dev/...`. On 2026-10-18 `pcp.dev` resolved to a Cloudflare host returning HTTP 525. Phantazein does not own it (confirmed 2026-10-19), so the published `$id`s point at a domain someone else controls. | Decision D9 (settled: GitHub Pages) |
| S21 | §10 | Conformance names six sections but no checkable list exists on `main`. | Phase 5 |

## 4. MultiPass vs the spec

MultiPass is the hosted personal product (`functions/_middleware.js` = `MW`,
`functions/pcp/[handle].js` = `EP`, `functions/api/_lib.js` = `LIB`).

### 4.1 Divergence table

| Area | Spec says | MultiPass does | Verdict |
|---|---|---|---|

| Provenance and gaps | `docs/profile-bootstrap.md` | Implemented as described, served on `/api/me` only (`LIB:73-99`) | Matches |
| `context.brief` | Profile + top-relevance memory | Profile + 5 newest pages; listed under `profile.core:read`, fails at call time without `memory:read` (`EP:181-195`) | Partial |
| `audit.list` | SHOULD | Not exposed | Missing |

### 4.2 What the spec should absorb from MultiPass

1. The OAuth discovery profile: PRM at root and path-suffixed, 401 with
   `resource_metadata`, metadata with HTTP 200 and no redirects, JSON 404 for
   unknown well-known paths.
2. `context_url_template` (or a renamed equivalent) for multi-context roots.
3. Server `instructions` that tell the client to treat the server as the
   source of truth and search before answering. Clients ignored memory
   servers until this was added (`LAUNCH.md:47`).
4. The consent screen naming the target context and the signed-in account.
5. A stable grant (token family) id that survives refresh rotation.
6. Audit entries that carry categories, never content.

Keep out of the spec: the `/pcp/{handle}` layout, handle rules, magic-link
and waitlist gating, token prefixes, `realm="multipass"`, Cloudflare and D1,
pricing and promise wording.

## 6. pcp-wp (paused) as prior art

pcp-wp built memory over MCP and a PACK importer, then paused when the
hosted product moved to Cloudflare.

| Spec area | pcp-wp | Reuse |
|---|---|---|
| §3 auth | Application passwords only, no OAuth | Shows a minimal revocable credential for localhost |
| §5.1 frontmatter | All v0.2 keys stored as registered post meta with enums and sanitizers (`includes/class-pcp-memory-post-type.php:97-183`) | Basis for a memory-page frontmatter JSON Schema |
| §5 paths | Lowercase, `.` to `-` | **Do not reuse**; it is why the spec needs a path grammar (S8) |
| §6 tool names | `pcp-memory-*` via the adapter's sanitizer | The adapter's `mcp_adapter_tool_name` filter accepts `[a-zA-Z0-9_.-]`, so a WordPress server **can** emit spec names (`RegisterAbilityAsMcpTool.php:221`) |
| §8 import | PACK importer: idempotent by path and hash, keeps raw frontmatter and dates, sensitive-by-directory default | Import conformance cases (fixtures in `tests/fixtures/pack`) |
| Encryption design | Runtime vs vault split; passkey PRF + recovery key; embeddings are content; exports always encrypted (`docs/encryption-and-identity.md`) | Input to Phase 4 |
| Work vs personal | D1 options (a) personal only, (b) personas in one context, (c) separate contexts | Input to Phase 4 |
| Bugs not to copy | `wp_kses_post` on memory content; `show_in_rest` on the memory post type (possible public listing; unverified); duplicate paths; instructions naming the wrong tool | Agent Brain review checklist |

Reusable import test cases: dotfiles skipped, no-frontmatter file, `legacy/`
skipped, index skipped, title from `topic`, literal `<not-a-tag>` and
backslashes preserved, unknown keys preserved, block lists with quotes,
idempotent re-import with dates kept.

### 9.1 Tool names

| Source | Rule | Dots? |
|---|---|---|
| MCP 2026-07-28 tools page (from SEP-986, Final) | SHOULD be 1 to 128 chars, case-sensitive, `A-Z a-z 0-9 _ - .`; no slashes | Allowed |
| Anthropic Messages API | `^[a-zA-Z0-9_-]{1,128}$` | No |
| Claude connector directory | 64 chars or fewer; every tool needs `title` and `readOnlyHint` or `destructiveHint` | n/a |
| OpenAI function calling | `^[a-zA-Z0-9_-]{1,64}$` (from API errors and community reports; official page not loaded) | No |
| Claude Code | Prefixes `mcp__<server>__`; dots shown as underscores (observed in this session) | Rewritten |
| OpenAI Codex CLI | Replaces everything outside `[A-Za-z0-9_]` with `_`, hyphens included | Rewritten |
| Cursor | Dots replaced with underscores (staff, 2026-04-14); 60-char limit on server + tool | Rewritten |
| Antigravity | Enforces `^[a-zA-Z0-9_-]{1,64}$`; rejected `memory.*` names | Rejected |
| WordPress mcp-adapter 0.6.1 | Ability `ns/verb` becomes `ns-verb`; a filter can emit `[a-zA-Z0-9_.-]` | Possible |

**Finding.** Dots are legal MCP but are rewritten or rejected by most
clients, and the model then sees a name that the server's own `instructions`
do not mention. Hyphens are rewritten by Codex. Only `[a-z0-9_]` passes
unchanged everywhere. Recommendation in [`v0.3-plan.md`](v0.3-plan.md),
decision D1: `<part>_<verb>`, lowercase, at most 40 characters.
OAuth scope strings (`memory.sensitive:read`) are unaffected: RFC 6749
allows dots and colons, and scopes never reach the model.

Client behavior worth writing into the spec: Claude needs a 401 to start
sign-in, uses only the first `authorization_servers` entry, requires PRM
`resource` to equal the URL as typed, uses `https://claude.ai/api/mcp/auth_callback`,
and gives discovery and token endpoints 10 seconds. ChatGPT prefers CIMD
(`https://chatgpt.com/oauth/client.json`). Sources:
[Claude](https://claude.com/docs/connectors/building/authentication.md),
[ChatGPT](https://developers.openai.com/apps-sdk/build/auth).

"Tokens per client-device pair" (S5): with CIMD every install of a client
shares one `client_id`, so the device can only be the grant and its refresh
family. v0.3 should say exactly that.

### 9.4 Memory and profile work in MCP

None is active. No working group, interest group, `ext-*` repository or open
SEP covers memory, profile or personal context. Closed without a sponsor:
SEP-2072 (Memory Portals), SEP-2342 (Memory Interchange Format, closed
2026-03-07; a core maintainer said memory formats are "probably" outside
MCP), issue #2043 (memory portability tools), issue #2681. Outside MCP, a W3C
AI Agent Memory Interoperability Community Group adopted a charter on

**Consequence.** The v0.2 §11 alignment trigger ("if an MCP memory/profile
extension is ratified, map onto it") has no near-term target. PCP should
publish itself as a third-party MCP extension, and later seek an interest
group sponsor if it wants an official Extensions Track SEP.

### 10.2 Regulation

| Instrument | Bearing on PCP |
|---|---|
| GDPR Art 20 | Covers data the person provided, read by WP242 to include observed but not inferred data. LLM-extracted memories are arguably inferred, so Art 20 may not require their export. PCP exports them anyway (principle 1). A `source.basis: provided \| observed \| inferred` field lets a host show which duty applies. |
| DMA Art 6(9) | Continuous, free portability of data "provided or generated", for gatekeepers only. No AI-assistant designation confirmed (*unverified*). |
| EU Data Act | Cloud-switching duties apply since 2025-09-12; switching charges end 2027-01-12. Relevant to hosted work and team contexts: a host must let a customer leave, and a PCP export is that exit. |
